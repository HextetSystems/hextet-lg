# M6.1 — Post-1.0 Security Audit

**Audit date:** 2026-11-12  
**Assessment:** Ready with conditions for a controlled public deployment behind a correctly configured TLS reverse proxy, after the test suite is brought back to a passing baseline and the low-severity enrichment issue below is addressed or explicitly accepted.

## Executive summary

The reviewed implementation has a strong set of practical protections for a read-only looking glass: public query parsing is bounded and strict; backend URLs are operator-configured; redirects are not followed; route JSON is streamed with byte and retention limits; HTML is rendered through `html/template` under a restrictive CSP; enrichment is optional and bounded; raw backend JSON and sensitive RTR addresses are withheld by default; and the container runs non-root with a read-only root filesystem and dropped capabilities.

One confirmed, low-severity trust-boundary issue remains: `/map` accepts caller-provided path data and schedules ASN DNS enrichment from it. With ASN enrichment enabled, an unauthenticated caller can induce bounded Team Cymru lookups for eligible ASNs of their choice. This does not create arbitrary DNS names or arbitrary network connections, and the feature is disabled by default.

The ordinary and race Go suites both fail in the current checkout. Several failures are direct implementation/test expectation mismatches (including `/summary` route expectations, duplicate `/neighbors` expectations, and neighbor navigation); others concern result rendering, fixtures, or load timing. This audit did not alter code or tests to diagnose/fix those failures. Browser tests and dependency vulnerability scanning were unavailable. The application's README already documents important deployment conditions, especially that the sample Compose file publishes plain HTTP on host port 8080 and must not bypass the TLS proxy.

## Scope and methodology

Reviewed current source and tests across `internal/web`, `internal/bgp`, `internal/config`, `internal/asn`, `internal/ptr`, `internal/site`, `internal/theme`, `internal/communities`, `cmd/hextet-lg`, the Dockerfile, Compose file, and security/deployment documentation. Traced public inputs through validation, backend requests, parsing, retained state, templates, headers, logs, metrics, and enrichment side effects. Treated public HTTP input, backend responses, DNS results, and operator configuration as separate trust boundaries.

Tools actually used:

- Repository inspection with `rg`, `git status`, and line-numbered source review.
- `go vet ./...` — passed.
- `go test ./...` — failed; failure summary is in [Test coverage gaps](#test-coverage-gaps). First sandbox attempt could not bind `httptest` loopback listeners; rerun with loopback access reached the tests and produced the listed failures.
- `go test -race ./...` — same failure set; no race report was emitted before the failing tests stopped the package run.
- `node --test internal/web/testdata/*.test.js` — passed (6 files).
- Checked tool availability: Node 20.19.2 and Docker CLI are present; Playwright, `govulncheck`, and `staticcheck` are unavailable. No tools were installed.

No production backend, public endpoint, external DNS service, or live deployment was contacted. No application code, configuration, dependencies, or tests were changed.

## Findings

### Low — Caller-controlled route-map data can trigger external ASN lookups

**Affected code:** `internal/web/route_map.go:108-177`, especially lines 146-177; `internal/web/route_map.go:217-270`; `internal/web/asn.go:77-120`; `internal/asn/asn.go:141-182`.

**Trust boundary and scenario:** `/map` is a public GET endpoint. It accepts a URL-safe base64 JSON `data` value from the caller, decodes up to 3 KiB and at most 128 paths, and builds a map from those values. The accepted AS-path tokens become ASN nodes (`buildRouteMap`); the handler then calls `scheduleASNs` on that map. When `asn_enrichment.enabled` is true, each eligible ASN can be queued for a DNS TXT lookup at `AS<number>.asn.cymru.com`.

**Evidence:** `routeMap` decodes and validates the supplied payload at lines 136-160, calls `buildRouteMap` with those decoded paths at line 162, and calls `h.scheduleASNs(&Page{Active: "map", Map: model})` at line 177. `buildRouteMap` parses numeric ASNs from the supplied path and marks eligible ASNs for enrichment at lines 258-270. `scheduleASNs` schedules those values at lines 83-95, and the worker sends the TXT lookup at `internal/asn/asn.go:179-182`.

**Impact and prerequisites:** With ASN enrichment enabled, an unauthenticated visitor can induce DNS traffic for selected eligible ASN numbers through the configured resolver. This can disclose lookup choices to the resolver/provider and consume bounded resolver capacity. The request rate limiter, 64-lookups-per-page default, fixed worker pool and queue, ASN eligibility checks, cache, and default-off enrichment limit impact. This is not arbitrary DNS-name injection, SSRF to arbitrary hosts, or an unbounded worker creation issue.

**Proportionate remediation:** Avoid scheduling enrichment from caller-supplied map payloads unless the payload is authenticated or its ASNs are matched against server-originated route data. A simpler alternative is to omit asynchronous enrichment from `/map` pages and retain the labels and ASNs already present in the map.

## Existing protections verified

- **Routing and request input:** Go's method-aware `ServeMux` exposes a small fixed route set; feature-disabled views are not registered. `guard` sets security headers, caps request URI/query length and parameter count, parses malformed query strings strictly, rejects unknown/repeated parameters on fixed routes, and rate-limits by the direct peer. Forwarded identity headers are not trusted. Route filters reject unknown, repeated, malformed, non-ASCII/control and invalid combinations rather than broadening a query.
- **Backend transport:** Backend addresses originate in validated configuration. Config validation limits schemes to HTTP(S), excludes URL credentials/query/fragment, and requires a configured backend. The client requests only the fixed bgplgd paths, uses request contexts/timeouts, and has `CheckRedirect` disabled. RIB bodies are incrementally decoded and size-limited; overview/RTR responses have tighter limits. Non-2xx responses and empty rejected-query responses are failures, not empty results.
- **Rendering and response handling:** Templates use `html/template`; route, neighbor, branding, community, and enrichment values remain data and are escaped. Plain text paths neutralize control characters. CSP disallows inline script/eval and external origins; standard security headers are applied by the outer handler. Error messages use fixed or bounded content and do not reflect invalid markup.
- **Resource control:** Request URL/header limits, read timeouts, bounded work admission, bounded backend fan-out, query timeout/queue/expensive-query gates, route response and retained-memory budgets, cache limits, write deadlines, and bounded ASN/PTR worker queues are present. ASN and PTR status endpoints are cache-only. The configuration and README explicitly state that accounting and `GOMEMLIMIT` are estimates/soft limits, not an RSS ceiling.
- **Disclosure defaults:** Raw JSON, RTR validator addresses, metrics, ASN enrichment, PTR enrichment, persistence, and external community definitions are opt-in or disabled by default as documented. Visibility exclusions are applied before retained/cached routes and enrichment.
- **Operational hardening:** The runtime image uses UID/GID 10001, a read-only root filesystem, dropped capabilities, `no-new-privileges`, a PID limit, read-only configuration mounts, and a health check. The optional metrics listener is separate from the public mux and defaults to loopback.

## Test coverage gaps

The current security tests meaningfully cover hostile HTML/backend/DNS values, redirect rejection, request validation, route exclusion, raw-data defaults, RTR address privacy, headers/CSP, enrichment bounds, reverse-proxy path-only URLs, and lifecycle cleanup. The map test verifies that legitimate map paths schedule ASN enrichment, but does not distinguish server-originated payload from a caller-forged payload; the finding above identifies that missing negative case.

The deterministic test runs are not green in this checkout. `go test ./...` and `go test -race ./...` report the same failures, including:

- `TestM52SecurityHeadersOnEveryKindOfResponse`: duplicate `/neighbors` expectations disagree (the test expects both 200 and 404 for the same default-enabled route).
- `/summary` assumptions in shutdown, neighbor-navigation, and observability tests: current `Routes()` registers `/neighbors` and `/rtr`, not a public `/summary` page. Backend `/summary` requests are still part of the `/neighbors` handler.
- ASN enrichment, neighbor navigation, rendering/golden, example-community count, disconnect admission, and mixed-load recovery expectations also fail.

These failures are not evidence by themselves of a security vulnerability, but they prevent treating the regression suite as a reliable security release gate until the expected behavior and implementation are reconciled. The detailed failure output from the run should be retained with the release triage. The optional Playwright suites were not run because Playwright is not installed; the Node-only JS tests do not substitute for browser CSP/history verification. No dependency CVE scan was possible because `govulncheck` was unavailable.

## Deployment-dependent risks

- The application speaks plain HTTP and intentionally omits HSTS. Terminate TLS at the reverse proxy, set HSTS there, and publish only the proxy. `compose.yaml:13-18` maps `8080:8080` on all host interfaces by default; the README advises binding it to loopback/internal networking when a proxy runs on the host. Exposing that mapping directly allows clients to bypass proxy TLS, per-client controls, and other proxy policy.
- The built-in rate limiter keys on `RemoteAddr`. Behind a proxy, all users share the proxy's bucket; per-client abuse controls and connection/rate limits must be enforced at the proxy. Do not add forwarded-header trust without an explicit trusted-proxy design.
- Backend URLs are intentionally trusted operator input and can point to internal addresses. Protect configuration files and restrict egress so a compromised/misconfigured backend configuration cannot use the application to reach unintended internal HTTP services. Public request parameters cannot change backend URLs, and redirect following is disabled.
- ASN enrichment sends eligible ASNs to Team Cymru DNS; PTR enrichment sends eligible next-hop/visible neighbor addresses to the configured resolver. Both are disabled by default and bounded. Enabling either is a deliberate disclosure of lookup data to the resolver/provider; private PTR addresses can reveal internal topology to that resolver.
- Metrics have no application authentication. Keep the separate listener loopback-only or restrict it to a trusted management network, and do not publish it publicly.
- Public IPv4/IPv6 reachability, a real production proxy/CDN, sustained production traffic, and a dependency/image vulnerability inventory were not verified in this audit. Container base references (`golang:1.27-alpine`, `alpine:3.21`) are tags rather than digests; release builds should keep base-image updates and provenance under active review.

## Prioritized remediation plan

1. **Before public release:** Resolve the failing Go test baseline, especially the routing/feature-gate expectations and resource/load tests, then rerun `go vet`, ordinary tests, race tests, and the browser suites in an environment with Playwright. Make the expected route surface explicit.
2. **Low-severity code change:** Stop caller-controlled `/map` payloads from triggering ASN enrichment, or authenticate/match their ASNs to backend-originated data. Add a test proving a forged map does not schedule DNS lookups.
3. **Before deployment:** Bind the app port to a private/loopback interface behind the TLS proxy; enforce HTTPS/HSTS, per-client rate/concurrency limits, and request-size limits at ingress. Keep metrics on a restricted management interface.
4. **Operational maintenance:** Run an approved dependency vulnerability scanner and image/base-image scan in CI or release validation; update/pin base images according to the project's reproducibility and patching policy.

## Limitations and unverified assumptions

- This was a source-and-test audit, not a penetration test, fuzzing engagement, live backend test, or sustained resource benchmark.
- No production systems or external DNS services were contacted; DNS privacy implications are inferred from the resolver call paths.
- The available environment had no Playwright or `govulncheck`/`staticcheck`, and no vulnerability database or image scan was performed.
- The test suites fail as described. Because the requested scope was read-only apart from this report, failures were not repaired and were not independently adjudicated as intended-product changes versus stale tests.
- Deployment readiness assumes the documented reverse-proxy and network restrictions are actually enforced, backends and configuration are operator-controlled, and opt-in data disclosures are reviewed by the operator.

## Assessment

**Ready with conditions.** The source review found no critical or high-severity issue in the public request-to-backend or backend-to-HTML paths. The low-severity map enrichment issue is bounded and requires ASN enrichment to be enabled, but should be corrected or explicitly accepted. Public exposure should wait until the currently failing Go regression suites are reconciled and the deployment conditions above are verified.
